# 0005 — 刺激の経路、音声ファイルの扱い、再生と刺激の時刻合わせ

**読者:** 実装者(本人とコーディングエージェント)。
**日付:** 2026-09-24
**状態:** 採用(Phase 2)

## 問い

音をどうやって「内部更新に作用する刺激」に変えるか。MP3 しか手に入らない音源(Suno の出力)をどう扱うか。窓アプリで聞こえる音と、モデルが受け取る刺激の時刻をどう合わせるか。

## 決定

1. **刺激はスカラー振幅 s(t) ∈ [0,1] と空間の形 h(x) の組。** モデル側の入り口は Lenia の `stim_mode` で選ぶ。`growth` は成長関数に `gain·s·h` を加算、`mu` は `mu_eff = mu + gain·s·h`。振幅 0 または `none` では Phase 1 の演算に一切触れない(テストでバイト一致を保証)。
2. **音の特徴量は RMS のみ。** 1 シミュレーションステップ分の実時間(既定 1/60 秒)を窓にした RMS を、ファイル全体の最大 RMS で正規化して [0,1] にし、指数移動平均(時定数 tau、既定 0.05 秒)で平滑化する。正規化の基準値は `config.json` と `summary.txt` に記録する。周波数帯の分解は Phase 2 では行わない。
3. **C++ 側は WAV だけを読む。** PCM 16/24/32 bit と float 32 bit、多チャンネルは平均。MP3 などは `scripts/to_wav.sh`(ffmpeg)で 44.1 kHz モノラル 16 bit の WAV に変換してから使う。
4. **窓アプリでは音声の再生クロックを主とする。** `--wav` を与えると SDL3 の audio ストリームで再生し、「再生済みバイト数」から求めた時刻に対応するステップまでシミュレーションを進める。停止で再生も止め、リセットでストリームを積み直す。WAV なしのときは Phase 1 と同じ実時間の累積で進める。
5. **実時間の時間基準は 60 steps/s。** ステップ k は実時間 k/60 秒に対応する。Orbium の dt=0.1 なので、シミュレーション時間 1 単位 = 実時間 1/6 秒。

## 理由

- 振幅と形を分けておくと、「何が入ったか」を `stimulus.csv` 1 本で再現でき、入り口の比較(growth と mu)を同じ入力で行える。
- RMS だけなら依存なしで実装でき、まず「音量に反応するか」を確かめられる。帯域ごとの応答は、それが必要だと分かってから足す([01_architecture.md](../01_architecture.md) の音声経路の順序どおり)。
- MP3 デコーダを組み込むと依存が増え、ライセンスと移植の確認が要る。ffmpeg は VM にあり、Mac なら brew で入る。
- 音声デバイスのクロックと壁時計は少しずつずれる。再生クロックを主にすれば、聞こえる音と刺激の時刻が長時間でもずれない。VM では SDL の dummy ドライバで同じコードパスを検証できる。

## 見送った案

- 単一ヘッダの MP3 デコーダ(minimp3 / dr_mp3)を同梱する: 依存は小さいが、Phase 2 の目的(音量への応答)には変換で十分。
- 壁時計で刺激を進め、音は独立に再生する: 実装は単純だが、ずれが蓄積する。
- 周波数帯(低音・高音)を分ける: Phase 2 の範囲外。RMS で応答が見えなければ、帯域分解より先に反応の強さ(コードでは `stim_gain`)や入り口を疑う。

## 再検討する条件

- 実機で再生クロック主導の同期が不安定(飛び・遅れ)なら、壁時計主導に戻して差を測る。
- 作品として「低音に反応する」表現が必要になったら、帯域分解を Phase 2 の追加または Phase 3 で扱う。
- MP3 を直接読む必要が本人の作業手順上どうしても要るなら、dr_mp3(public domain)を検討する。

## 実機での確認(2026-09-24、本人、Mac)

`cave_window --wav` で kick120 / tone を再生しながら観察。一様な刺激(growth 0.2)は違いがほとんど分からず、勾配(gradient_x)は向きが変わって分かりやすかった。音声の再生自体は動作した。同期のずれについての指摘はなし。追加実験で一様な安全域の上限は反応の強さ 0.3(0.4 で飽和)と判明。
