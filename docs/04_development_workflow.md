# 04 — 開発の進め方

**読者:** 本人(制作者)。
**役割:** 1 つのフェーズをどう回すかを、人間側の視点で書く。エージェントが常時守るルールは [CLAUDE.md](../CLAUDE.md)、報告の様式は [.claude/skills/phase-report/SKILL.md](../.claude/skills/phase-report/SKILL.md) に分けてある。

## 1 フェーズのサイクル

```text
本人: README の「現在のフェーズ」を確認し、phases/ の文書を具体化する
  ↓
エージェント: フェーズ文書に従って実装・実行・記録する
  ↓
エージェント: /phase-report の様式で報告する
  ↓
本人: 映像と数値を自分で観察し、次に進むか、戻るか、保留するかを決める
  ↓
本人: push して PR を作り、マージする(フェーズごとに 1 本)
  ↓
本人: README の「現在のフェーズ」を書き換え、次の phases/ 文書を具体化する
```

## 本人がやること

1. **フェーズを始める前に**、[phases/](phases/) の該当文書に実装範囲と完了条件が書けているか確認する。草案のままなら具体化する。
2. **エージェントに渡す指示文**は、各フェーズ文書の末尾「エージェントへの指示文」を使う。
3. **報告を受けたら**、映像と数値を自分の目で確認する。「うまくいった」という言葉ではなく、指標で判断する。
4. **次へ進むと決めたら**、フェーズのブランチを push し、PR を 1 本作ってマージする。エージェントは commit まで行い、push と PR は本人の役割にしてある([CLAUDE.md](../CLAUDE.md) の「Git の運用」)。
5. **マージ後**、README の「現在のフェーズ」を書き換える。エージェントはそこを作業範囲として読む。
6. **設計を変えたくなったら**、[decisions/](decisions/) に短く残す。
7. **疑問が出たら**、[learning/](learning/) に書く。コードで確かめた結果と出典を添える。

## 守りたいこと

- 先のフェーズを先取りしない。長期の構想があっても、今のフェーズに含めない。
- 観察していないことを記録に書かない。
- 各フェーズの終わりに、本人の確認を必ず挟む。エージェントに判断を委ねない。

これらは [CLAUDE.md](../CLAUDE.md) にも書いてあり、エージェント側でも守られる。
